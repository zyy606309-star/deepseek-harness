# 🛡️ 网易盾无感验证码逆向执行版

> 面向 LLM 的低 token 执行工作流。目标不是重讲原理，而是把一次完整测试压缩成可控阶段、可复用记录和最小上下文。
> 如果要和仓库统一规范对齐，开始前先过一遍 [00_JS逆向作业规范.md](/D:/网易/crawler-mcp/skills/00_JS逆向作业规范.md)。

> 本文是执行模板，不是协议说明。接口名、参数位置、SDK 文件名和成功判据必须以当前轮次证据为准。

---

## 一、文档定位

本文档负责：

- 控制阶段边界
- 规定每阶段最小证据
- 规定什么时候停止继续深挖
- 把问题压缩成低 token 工作流

本文档不负责：

- 详细解释网易盾原理
- 提供长篇背景资料
- 直接给 Claude / GPT 的投喂模板

配套文件：

- 原理版：`06_网易盾无感验证码逆向_原理版.md`
- 提示词版：`08_网易盾无感验证码逆向_提示词版.md`

推荐使用顺序：

1. 如需理解整体链路，先看原理版
2. 真正开始做测试时，以本文档为主线
3. 和 AI 多轮交互时，再调用提示词版

---

## 二、用途

在以下情况使用本工作流：

- 已知目标是网易易盾无感验证码
- 需要验证或修复 `fp`、`cb`、`data.m/p/ext`
- 需要控制 LLM token 消耗
- 仓库中已经有可参考实现：`analysis/dun_sense/`

如果只是学习整体原理，先看 `06_网易盾无感验证码逆向_原理版.md`。如果目标是高效复测、版本漂移排查、快速修复，优先使用本文档。

---

## 三、核心原则

### 3.1 先验证现有实现，再决定是否逆向

默认假设 `analysis/dun_sense/` 仍有参考价值。先验证现有脚本和目标站点是否还匹配，再决定是否进入断点逆向。

### 3.2 每阶段只采集最小证据

每一阶段只保留能支持下一步决策的信息，不保留“看起来以后可能有用”的大段材料。

只保留：

- 目标页面 URL
- 触发选择器
- 4 条关键请求样本
- SDK 文件名和版本
- 必要常量
- 一条成功或失败的验证结果

### 3.3 禁止整段喂大文件

不要把以下内容整段贴给 LLM：

- 完整混淆 JS
- 完整调用栈
- 完整请求响应体
- 长截图 OCR 文本
- 整个 `flow.md`

只贴与当前问题直接相关的片段，单次片段尽量控制在 30 到 80 行。

### 3.4 每阶段必须产出摘要

每完成一阶段，立刻生成一份 100 到 200 字摘要。后续只引用摘要，不重复粘贴原始材料。

---

## 四、标准阶段

每个阶段开始前保留原始证据索引；结束时记录结果、置信度、未决问题和回退动作。摘要不能替代原始请求、脚本和日志。

### 阶段 0：建立基线

目标：

- 确认目标页面、触发方式、参考实现路径

必记录：

- 页面 URL
- 验证码触发元素选择器
- 当前参考目录：`analysis/dun_sense/`
- 当前日期
- 浏览器、Node、Python 版本
- 原始证据目录或文件哈希

完成标准：

- 能稳定打开页面并触发验证码
- 至少连续两次触发结果一致，或明确记录不一致原因

输出模板：

```text
[阶段0摘要]
页面:
触发选择器:
参考实现:
是否可稳定触发:
下一步:
```

### 阶段 1：抓请求链路

目标：

- 确认 `getconf`、`up`、`get`、`check` 是否完整出现

只抓这些信息：

- 请求 URL
- 方法
- 是否命中
- 请求中哪些参数出现：`fp`、`cb`、`data`、`token`
- 响应状态、响应类型和参数首次出现位置

不要保留：

- 全量 headers
- 全量响应体

完成标准：

- 四条关键接口全部确认
- 能说清每个参数首次出现在哪条请求
- 已保存请求摘要及其触发动作

输出模板：

```text
[阶段1摘要]
getconf:
up:
get:
check:
fp首次出现:
cb首次出现:
data首次出现:
token首次出现:
下一步:
```

### 阶段 2：先复测现有实现

目标：

- 判断 `analysis/dun_sense/` 是否仍然可跑

优先验证：

- `step1_ir_sdk_config.py`
- `step2_getconf.py`
- `step3_up.py`
- `step4_get.py`
- `step5_check.py`

只记录：

- 哪一步成功
- 哪一步失败
- 失败点是请求失败、参数失效还是版本漂移
- 运行命令、退出码和最小错误摘要

跳转规则：

- 如果 5 步全通，停止逆向，直接归档
- 如果只有单点失败，只分析该参数链路
- 如果多步都因参数失效失败，再进入后续断点阶段

输出模板：

```text
[阶段2摘要]
step1:
step2:
step3:
step4:
step5:
结论: 继续复用 / 局部修复 / 重新逆向
下一步:
```

### 阶段 3：仅在需要时逆 `cb`

进入条件：

- `cb` 相关步骤失败
- 或关键常量明显变化

最小动作：

- 对 `cb=` 设 XHR 断点
- 记录生成点附近的函数名
- 提取 `SEED_KEY`
- 提取 `S-Box`
- 提取 `变换序列`
- 提取 `code` 和 `suffix`
- 提取 Base64 字符集

不要做：

- 没有目标地单步几十轮
- 把整段混淆函数贴给 LLM 重写

完成标准：

- 已拿到足够重建 `cb_encoder.js` 的常量
- 每个常量都有来源位置和提取时间，未知项明确标记为未知

输出模板：

```text
[阶段3摘要]
断点位置:
SEED_KEY:
S-Box是否完整:
变换序列:
code:
suffix:
Base64字符集:
是否足够修复cb:
下一步:
```

### 阶段 4：仅在需要时逆 `data.m/p/ext`

进入条件：

- `step5_check.py` 失败且确认问题在 `data`

最小动作：

- Hook `encodeURIComponent`
- 只抓一次有效 `data`
- 定位轨迹数组、`p` 输入、`token` 输入、核心加密函数
- 提取内层字符集或关键变换逻辑

只记录：

- `data` 的结构特征
- 轨迹源变量
- token 进入点
- 编码字符集

不要保留：

- 整个 `data` 长串
- 大段堆栈截图

完成标准：

- 已足够修复 `data_encoder.js`
- 至少有一组浏览器同输入样本可用于回归

输出模板：

```text
[阶段4摘要]
data捕获方式:
轨迹变量:
p输入:
token输入:
编码函数:
字符集:
是否足够修复data:
下一步:
```

### 阶段 5：回填脚本并验证

目标：

- 把变更落实到 `analysis/dun_sense/`

只验证：

- 修复后的 `cb_encoder.js`
- 修复后的 `data_encoder.js`
- 完整 `step5_check.py`

只记录：

- 输入样本
- 输出长度或关键特征
- 接口最终返回
- 修改前后差异和回滚方式

完成标准：

- 关键脚本恢复可运行
- 最终请求通过
- 业务响应与浏览器结果具有相同的成功语义，而不是只有 HTTP 200

输出模板：

```text
[阶段5摘要]
修改文件:
cb验证:
data验证:
最终check结果:
结论:
```

## 五、低 Token 决策树

按以下顺序决策：

1. 先抓 4 条关键请求，确认链路完整。
2. 先跑 `analysis/dun_sense/` 现有脚本。
3. 只有失败时才决定修 `cb` 还是修 `data`。
4. 只修失败的那一段，不同时展开两个逆向线程。
5. 验证通过后立即停止，不继续“顺手深挖”。

6. 如果失败点无法归因到 `fp`、`cb`、`data` 或 `token`，先回到阶段 1 补请求证据，不要直接进入算法重写。

## 七、给 LLM 的喂料规则

### 6.1 单轮只解决一个问题

好例子：

- “这是 `step5_check.py` 的失败响应，请判断是 `cb` 还是 `data` 有问题。”
- “这是 `cb` 断点处的 40 行代码，请提取常量，不要解释原理。”

差例子：

- “这是全部脚本、全部请求、全部日志，帮我完整逆向。”

### 6.2 优先给摘要，不给原文

优先给：

- 阶段摘要
- 单条失败响应
- 单个函数片段
- 单个调用点

只有摘要不足以决策时，才补原始片段。

### 6.3 明确要求输出格式

要求 LLM 直接输出：

- 常量表
- 修复建议
- 需要修改的文件名
- 下一步动作
- 证据依据和置信度

禁止根据变量名、旧版本常量或单个样本补全未知协议；证据不足时必须明确输出“证据不足”。

避免让模型自由发挥长篇解释。

## 八、停止条件

出现以下任一情况就停止当前阶段：

- 已足够修复对应脚本
- 已确认现有实现可继续复用
- 问题定位到另一个参数链路
- 再继续只会增加材料，不会提高结论确定性

---

## 九、推荐顺序

推荐按以下顺序使用项目资料：

1. 本文档
2. `analysis/dun_sense/` 现有脚本
3. `06_网易盾无感验证码逆向_原理版.md`
4. 浏览器断点现场片段

不要反过来做。先读大文档、再全量看 JS、最后才想起跑现有脚本，是最容易烧 token 的路径。

## 十、典型预算

以“仓库已有可运行实现”为前提：

- 链路确认：`5k-10k`
- 现有脚本复测：`5k-15k`
- 单点修 `cb`：`10k-30k`
- 单点修 `data`：`15k-40k`
- 完整复测并收口：`5k-10k`

如果按本文档执行，常见任务应尽量压在 `20k-60k` 范围内。出现远高于这个量级的消耗，优先检查流程，而不是默认问题本身更复杂。
