# 瑞数处理

> 这是挑战页和动态 Cookie 的识别与复现笔记。特征只能用于建立假设，不能仅凭 Cookie 名称或后缀给站点定型。

## 一、特征识别

判断目标站点是否大概率使用瑞数，可以先看下面几个特征。

### 1. 打开开发者工具后出现大量 `debugger`

常见表现：

1. 一打开 DevTools 就不断断在 `debugger`
2. 很多断点都出现在 `VM` 脚本里
3. 页面明显存在反调试逻辑

这类现象本身不能单独证明一定是瑞数，但在瑞数站点上非常常见。

### 2. 关键加密参数主要体现在 Cookie

常见表现：

1. 首次请求后先下发一组服务端 Cookie
2. 页面 JS 执行后再生成一组新的 Cookie
3. 第二次请求是否成功，通常强依赖这组 JS 生成的 Cookie

所以遇到这类站点时，先重点观察 Cookie，不要一开始就只盯请求体或请求头签名。

### 3. 会出现两个很相似的 Cookie 字段

瑞数站点里，经常会看到两个名字非常相近的 Cookie，例如：

```text
NOh8RTWx6K2dS
NOh8RTWx6K2dT
```

观察重点不是前缀，而是末尾字符。

### 4. 瑞数 6 和瑞数 5 的一个常见区分方式

常见经验特征：

1. 瑞数 6 常见为末尾 `S / T`
2. 瑞数 5 常见为末尾 `O / P`

也就是说，如果看到类似：

```text
xxxxS
xxxxT
```

那么大概率更偏向瑞数 6。

如果看到类似：

```text
xxxxO
xxxxP
```

那么大概率更偏向瑞数 5。

注意：

1. 这只是经验特征，不是绝对规则
2. 真正判断时，仍然要结合页面行为、JS 结构、请求链路一起看

版本判断至少还要结合挑战脚本结构、Cookie 更新时序、响应头和二次业务请求结果。`S/T`、`O/P` 后缀不能单独作为版本判据。

## 二、如何复现

瑞数这类站点，复现的核心通常不是先研究复杂算法，而是先把页面下发的两段 JS 拿全。

这里的“两段 JS”通常指：

1. 挑战页里的第一段内联 JS
2. 挑战页引用的外链 JS

只要这两段拿对了，再配合当前轮次的动态输入，后面的本地执行才有意义。

### 1. 先拿首包挑战页

先发第一次请求，目标一般就是首页。

预期结果：

1. 返回内容可能是挑战页，状态码不一定区别于正常业务页；不要把“不是 200”当成必要条件
2. 返回的是挑战页 HTML
3. 页面里会带一段 `meta`
4. 页面里会带一段内联脚本
5. 页面里通常还会带一个外链脚本

这一步最重要的产物就是：

1. 挑战页 HTML
2. 首包服务端 Cookie

### 2. 从挑战页里提取第一段内联 JS

不要把所有脚本一股脑全取出来。

正确做法是：

1. 找到页面里第一个真正参与挑战逻辑的内联脚本
2. 一般就是第一个：

```html
<script type="text/javascript" r="m">...</script>
```

3. 只提取这一段的内容

这里要注意：

1. 有的页面不止一个 `script[type="text/javascript"][r="m"]`
2. 当前链路里只取第一个
3. 不要把后面的脚本混进来

### 3. 再提取外链 JS

除了内联脚本，还要找挑战页里引用的外链脚本。

常见形式：

```html
<script type="text/javascript" charset="utf-8" src="/xxxx.js" r="m"></script>
```

正确做法：

1. 从首包页面里拿到这个 `src`
2. 拼成完整 URL
3. 单独请求这个外链 JS
4. 把拿到的完整代码保存下来

### 4. 为什么说复现的关键是这两段 JS

因为后续本地执行时，主要依赖的就是：

1. 当前轮次的页面动态输入
2. 这段内联 JS
3. 这段外链 JS

少任何一段，或者拿错其中一段，后面生成出来的 Cookie 都很可能不对。

### 5. 这一步的正确顺序

顺序不要乱，固定按下面做：

1. 首次请求拿挑战页
2. 提取内联 JS
3. 提取外链 JS
4. 提取当前轮次动态输入
5. 再回到本地补环境执行

不要反过来：

1. 先写本地环境
2. 再猜脚本内容
3. 再猜输入值

这样很容易越做越偏。

### 6. 当前轮次还必须同步提取的东西

除了两段 JS，本轮页面里通常还要一起拿：

1. `meta content`
2. 首包服务端 Cookie

因为这两类东西和 JS 一样，都属于“当前轮次输入”。

如果 JS 是新的，但 `meta` 或 Cookie 还是旧的，最终结果一样会错。

### 7. 这一步的目标

做到这一步时，应该至少拿到下面这些产物：

1. 首包挑战页 HTML
2. 第一段内联 JS
3. 外链 JS
4. `meta content`
5. 首包服务端 Cookie

有了这些，才进入下一步：本地补环境执行 JS，生成 Cookie。

### 8. 复现验证

本地生成 Cookie 后，至少做一次浏览器/本地同轮次对照：

1. 挑战页 HTML 和两段脚本来自同一轮；
2. `meta`、服务端 Cookie 和动态输入没有跨轮次混用；
3. Cookie 属性、作用域和更新时间一致；
4. 二次请求的状态、响应内容和业务结果一致。
