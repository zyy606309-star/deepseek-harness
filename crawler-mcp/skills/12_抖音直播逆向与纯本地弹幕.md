# 抖音直播逆向与纯本地弹幕

> 用于分析抖音 Web 直播的 WebSocket/protobuf 链路，并将已验证的弹幕获取流程迁移到本地脚本。先用浏览器建立事实，再选择浏览器流、捕获握手后的本地 WebSocket，或纯本地 HTTP 拉取。

## 一、适用场景

看到以下目标或关键词时进入本专题：

- 抖音直播、直播弹幕、`WebcastChatMessage`
- WebSocket 握手、ACK、heartbeat、断线重连
- `/webcast/im/fetch/`、protobuf、gzip
- `a_bogus`、`room_id`、`cursor`、`internal_ext`
- 从浏览器抓包迁移到本地持续请求

开始前先读 [00_JS逆向作业规范.md](<D:/网易/crawler-mcp/skills/00_JS逆向作业规范.md>)。涉及大包定位或签名重逆时，再读 [10_webpack包处理.md](<D:/网易/crawler-mcp/skills/10_webpack包处理.md>)。

## 三、优先选择运行模式

```text
只要快速看弹幕
  -> 浏览器流模式

需要研究真实 WebSocket 帧、ACK、心跳
  -> 捕获握手后的本地 WebSocket 模式

最终目标是不依赖浏览器持续获取弹幕
  -> 纯本地 HTTP /webcast/im/fetch/ 模式
```

### 模式 A：MCP 浏览器流

1. 启动或连接真实 Chrome。
2. 打开直播间并等待 WebSocket 建立。
3. 调用 `start_live_stream`。
4. 循环调用 `read_live_messages`。
5. 结束时调用 `stop_live_stream`。

常用过滤：

```json
{
  "duration": 10,
  "max_messages": 200,
  "methods": ["WebcastChatMessage"]
}
```

需要检查底层帧方向和握手时，调用 `get_websocket_events`。事件中的 `direction` 为 `sent` 或 `received`。

### 模式 B：捕获握手后的本地 WebSocket

```powershell
python D:\网易\crawler-mcp\utils\douyin_live_direct.py `
  --port 9222 `
  --output D:\网易\crawler-mcp\artifacts\direct-live.jsonl
```

省略 `--duration` 时持续运行，直到手动停止。脚本会捕获当前 Chrome 的真实握手 URL 和 Cookie，本地连接 WebSocket；连接关闭后重新捕获握手并重连。

也可以短期复用已保存的材料：

```powershell
python D:\网易\crawler-mcp\utils\douyin_live_direct.py `
  --ws-url '<CAPTURED_WSS_URL>' `
  --cookie-file D:\path\to\cookie.txt
```

握手 URL 内的 `cursor`、`internal_ext`、设备标识和签名会过期。失效后回到浏览器重新捕获，不要把旧 URL 当成稳定配置。

### 模式 C：纯本地 HTTP 弹幕

```powershell
python D:\网易\crawler-mcp\utils\douyin_live_direct.py `
  --local-http `
  --room-url https://live.douyin.com/<WEB_RID> `
  --cookie-file D:\path\to\cookie.txt `
  --method WebcastChatMessage `
  --output D:\网易\crawler-mcp\artifacts\douyin-live-http.jsonl
```

该模式不连接 Chrome、CDP 或 WebSocket。省略 `--duration` 时持续拉取；按 `Ctrl+C` 停止。

## 四、纯本地 HTTP 请求链

```text
直播间 URL + Cookie
  -> GET /webcast/room/web/enter/?a_bogus=...
  -> 解析真实 room_id
  -> POST https://mcs.zijieapi.com/webid
  -> 获取 user_unique_id
  -> GET /webcast/im/fetch/?resp_content_type=protobuf&a_bogus=...
  -> 解析消息、cursor、internal_ext、heartbeat、push_server
  -> 使用新 cursor 和 internal_ext 继续请求
```

`web_rid` 是直播间 URL 路径中的号码，不一定等于服务端返回的真实 `room_id`。必须先调用 room enter 接口完成解析。

## 五、protobuf 结构

### HTTP fetch 响应

当前样本确认的外层字段：

| field | wire type | 含义 | 使用方式 |
|---|---:|---|---|
| 1 | 2 | 消息 envelope，可重复 | 解析 method 和 payload |
| 2 | 2 | `cursor` | 下一次请求原样携带 |
| 5 | 2 | `internal_ext` | 下一次请求原样携带 |
| 8 | 0 | heartbeat | 作为服务端节奏线索 |
| 10 | 2 | `push_server` | WebSocket 研究线索 |
| 14 | 2 | `push_server_v2` | WebSocket 研究线索 |

消息 envelope 当前解析：

- field 1：消息方法，如 `WebcastChatMessage`
- field 2：消息 payload
- chat payload field 3：弹幕文本
- chat payload field 2：用户结构
- user field 1：用户 ID
- user field 3，回退 field 2：用户名

这些字段来自当前真实样本和本地解析验证。新增礼物、点赞、成员进入等消息时，应按各自 method 单独恢复 payload schema，不要把 chat 的字段号无条件套用到所有消息。

### WebSocket 响应帧

浏览器收到的二进制帧为外层 protobuf，消息体包含 gzip 数据。当前实现通过 gzip magic `1f 8b` 定位压缩边界，解压后再解析消息 envelope。

## 六、ACK 与心跳

当前样本确认：

- ACK 外层 protobuf field 2：`msg_id`
- ACK 外层 protobuf field 7：`ack`
- ACK 外层 protobuf field 8：`im-internal_ext`
- 二进制心跳：`3a 02 68 62`
- 心跳周期：约 10 秒

ACK 与心跳属于 WebSocket 会话状态。若只使用 HTTP fetch 模式，不需要发送 WebSocket ACK 或该二进制心跳。

## 七、`a_bogus` 说明

当前本地生成入口：

```text
utils/douyin_live_direct.py
  -> utils/douyin_abogus_cli.js
  -> utils/douyin_abogus.js
```

重要边界：当前 `a_bogus` 实现不是本轮从最新抖音 bundle 从零恢复的算法，而是复用了本机已有工程 `D:\网易\crawl_spider\base_crawl\douyin\a_bogus.js`，随后对当前 room enter 和 IM fetch 接口做了真实业务验证。

因此当前结论是“现有实现对已测接口可复用”，不是“已证明与最新前端算法完全一致”。出现接口拒绝时，按以下顺序核对：

1. query 参数顺序和 URL 编码是否与签名输入一致；
2. `User-Agent` 是否与生成签名时一致；
3. Cookie、设备字段、Referer 是否来自同一会话语义；
4. 当前 bundle 是否更新了签名版本；
5. 用浏览器真实请求与本地请求做同输入对照。

## 八、Cookie 与登录态

登录态会直接影响 room enter、webid、IM fetch 和 WebSocket 握手的成功率。逆向与本地复现阶段应保留完整原始 Cookie 证据，不要为了“脱敏”破坏请求语义。

控制凭证风险的方式：

- Cookie 文件放在受控的任务产物目录；
- 不提交到版本库；
- 文档、报告和聊天摘要中不展开真实值；
- 失效或任务结束后删除或轮换；
- Cookie 与对应 User-Agent、房间 URL、采集时间一起记录。

## 九、断线、续接和停止语义

- `--duration 30` 表示运行 30 秒后正常输出 `direct_stopped`，不是异常断联。
- WebSocket 的 `direct_disconnected` 表示当前连接关闭；随后出现 `reconnecting` 和新的 `direct_started` 属于自动重连流程。
- HTTP 模式每轮必须使用响应返回的新 `cursor` 和 `internal_ext`。
- 房间结束、Cookie 过期、设备校验失败和网络超时应分开记录，不能统一归为“没弹幕”。
- 省略 `--duration` 才是持续运行模式。

## 十、常见错误

### `ModuleNotFoundError: No module named 'browser'`

脚本已通过把项目根目录加入 `sys.path` 修复。若再次出现，确认运行的是当前 `D:\网易\crawler-mcp\utils\douyin_live_direct.py`，而不是旧副本。

### `DEVICE_BLOCKED` / `handshake-status: 415`

说明手工拼接的 WebSocket URL 未通过设备握手校验。当前稳定回退是纯本地 HTTP fetch；继续研究时重点比较浏览器握手中的 signature、设备标识、cursor、internal_ext 和 header。

### room enter 没有返回房间数据

检查直播是否结束、`web_rid` 是否正确、Cookie 是否失效、`a_bogus` 与 query/UA 是否一致。

### 进程“自动中断”

先检查是否传了 `--duration`。有 `direct_stopped` 且时长符合参数时属于正常结束；有 `direct_disconnected` 后继续 `reconnecting` 属于连接重建。
