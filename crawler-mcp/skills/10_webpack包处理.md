# Webpack 包处理

## 一、适用场景

这篇文档处理的是一种很常见的情况：

1. 你拿到的不是单个普通 JS
2. 而是一个 webpack 打包后的大包
3. 你的目标不是跑整站
4. 而是只取其中某个模块里的加密函数或工具函数

先确认目标是“提取模块”还是“复现整站行为”。如果目标函数依赖运行时注入、动态 chunk、页面状态或浏览器 API，单独取模块只能作为定位步骤，不能默认等价于整站执行。

这类情况下，重点不是补完整站环境，而是先把 webpack 的模块加载器理出来。

---

## 二、如何判断是 webpack 包

看到下面这些特征时，基本就要往 webpack 方向想：

1. 存在 `window.webpackJsonp`
2. 存在一个很大的模块表对象
3. 存在模块缓存对象
4. 存在形如 `function o(t)`、`function n(t)` 的模块加载函数
5. 存在 `e[t].call(...)` 这种执行模块的形式

典型结构一般像这样：

```js
!function(e) {
    var n = {};
    function o(t) {
        if (n[t]) return n[t].exports;
        var i = n[t] = {
            i: t,
            l: false,
            exports: {}
        };
        return e[t].call(i.exports, i, i.exports, o),
        i.l = true,
        i.exports;
    }
}( ... )
```

这里通常：

1. `e` 是模块表
2. `n` 是模块缓存
3. `o` 是模块加载器

---

## 三、第一件事不是补环境，而是找加载器

遇到 webpack 包，先不要急着补：

1. `window`
2. `document`
3. `navigator`
4. 各种 DOM

第一件事是先确认：

1. 哪个函数是模块加载器
2. 目标模块的模块 id 是多少

同时记录：Webpack 版本线索、runtime 文件、chunk 加载方式、模块表是否可枚举、exports 形态和入口副作用。

如果加载器都没理清楚，后面补环境很容易越补越偏。

---

## 四、入口模块自动执行通常要先停掉

webpack 包里经常会看到类似：

```js
o(o.s = 0)
```

这句通常表示：

1. `o` 是模块加载器
2. `0` 是入口模块
3. 这句代码会直接启动整个前端应用

如果你的目标只是拿某个模块里的加密函数，这句通常应该先停掉。

不要机械删除入口调用。先复制原包，在副本中做最小改动，并验证 loader、模块缓存和 chunk 注册仍然可用。某些包的入口会负责注册动态模块、初始化 polyfill 或注入关键常量，直接删除会改变目标模块行为。

### 为什么要先停掉

因为入口模块一旦执行，整站逻辑就都会跑起来。

常见后果：

1. 立刻访问 `window.navigator`
2. 立刻访问 `document`
3. 立刻跑框架初始化
4. 立刻跑路由和环境识别
5. 报出大量与你真正目标无关的环境错误

所以这里的基本原则是：

如果目标只是拿某个模块，不要先把整站入口跑起来。

---

## 五、正确做法：先挂加载器，再单独取模块

更合适的顺序是：

1. 先停掉入口模块自动执行
2. 把 webpack 的模块加载器挂到全局
3. 再按模块 id 单独取目标模块

例如，假设内部加载器是 `o`：

```js
window.loader = o;
```

之后再调用：

```js
window.loader("6c27")
```

只有在确认模块表和 loader 都已经初始化后，才能这样调用。Webpack 5、动态 chunk 或闭包私有 loader 不一定存在可直接挂出的 `o`。

这样做的好处是：

1. 不启动整站
2. 只执行目标模块
3. 补环境范围可以缩到最小

---

## 六、为什么这样做更稳

“整站入口”和“目标模块”对环境的要求完全不是一个量级。

如果直接跑整站入口，你需要补的是：

1. 框架环境
2. 路由环境
3. DOM
4. 浏览器特征
5. 页面初始化逻辑

如果只是单独取目标模块，你通常只需要补：

1. 少量全局对象
2. 少量工具函数
3. 少量动态输入

这两者工作量不是一个量级。

---

## 七、标准处理步骤

以后遇到 webpack 包，默认按这个顺序做：

### 1. 找模块加载器

确认哪个函数是真正的 webpack require。

### 2. 找入口自动执行代码

常见就是：

```js
o(o.s = 0)
```

先停掉它。

### 3. 挂全局 loader

例如：

```js
window.loader = o;
```

### 4. 按模块 id 试取模块

例如：

```js
window.loader("6c27")
```

### 5. 看模块 exports

确认里面到底导出了什么：

1. 函数
2. 对象
3. 默认导出
4. 命名导出

### 6. 再补最小环境

对模块做三组对照：浏览器原模块输出、本地模块输出、禁用某个依赖后的输出。至少保留同一输入下的结果长度、类型、关键字段和异常差异。

只针对这个模块运行时真正访问到的东西去补，不要提前补整站。

---

## 八、常见误区

### 1. 一上来就跑入口模块

错误后果：

1. 整站启动
2. 大量无关错误
3. 很难判断真正目标模块到底依赖什么

### 2. 还没挂 loader 就在外面瞎调用

错误写法：

```js
window.loader("6c27")
```

但实际上 `window.loader` 根本没挂出来。

正确做法是先把内部加载器挂到全局。

### 3. 把 webpack 包当普通单文件补环境

这会导致：

1. 补环境范围无限扩大
2. 你补的是整站，不是目标模块

### 4. 还没确认模块 id 就乱试

模块 ID 不是跨版本稳定标识。不要把某个成功案例中的 `6c27`、入口 `0` 或函数名当成通用规则；应从当前 runtime、模块表或调用栈重新确认。

先定位目标模块，再谈调用。

---

## 九、一句话总结

先恢复当前包的 loader/runtime，再做模块切片；切片后的结果必须用浏览器同输入样本验证，不能只凭“能调用”判断成功。

如果目标只是拿加密函数，不要先把整个 webpack 应用跑起来。
